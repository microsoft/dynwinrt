## Unreleased (next preview)

Candidate directions after the preview.23 baseline: broader checked collection support, JavaScript/Python Object-conversion parity, and smaller generated bindings. These are proposed priorities, not completed features or a commitment to ship every item in the next preview.

### Checked POD vector inputs

Review and integrate the proposed [POD vector work (#179)](https://github.com/microsoft/dynwinrt/pull/179) against current main as the first milestone of [struct collection support (#161)](https://github.com/microsoft/dynwinrt/issues/161). This would let generated JavaScript arrays and Python sequences supply more validated WinRT structs, including ARM64 floating-point aggregates and larger or nested POD layouts. Current checked constructors already accept a limited ABI-safe subset; this is an expansion, not support from zero. Keep maps, structs containing owned references, and metadata-free unsafe constructors outside this milestone.

Acceptance should cover SDK-typed native x64 and ARM64 vector/view/iterator calls, packed bulk buffers, independent snapshots, observable reentrancy, exact type/IID identity, and rejection of unsupported layouts or ownership. Do not equate merging #179 with completing #161.

### JavaScript/TypeScript Object-value parity

Bring the explicit Object-conversion facilities added for Python to JavaScript/TypeScript: type-aware boxing, typed unboxing, and an opt-in live view over supported Object-valued maps. Start from the shared core PropertyValue model; JavaScript currently still rejects DateTime, TimeSpan, geometry, InspectableArray, and their applicable array forms even though the core models those payloads. Keep ordinary generated Object results raw and preserve non-PropertyValue object identity.

Define number/bigint type selection and date/time precision before enabling new conversions. Acceptance should include exact PropertyType round trips, range and precision boundaries, real PropertySet/map operations, strict TypeScript declarations, and unchanged errors for invalid or unsupported input. Avoid implicit conversion or renderer-level type guessing.

### Smaller generated JavaScript

Address [duplicated implementation helpers (#182)](https://github.com/microsoft/dynwinrt/issues/182) by emitting common private helpers once per generated package instead of copying them into every implementation-capable interface module. Start with deduplication without removing interface implementation support or its validation checks.

Rebaseline against preview.23 using pinned metadata and identical generation options. Record generated bytes, file count, and cold-import cost; verify CJS/ESM loading, custom runtime imports, incremental generation, declarations, callback behavior, and import-cycle safety. The older issue's size measurements are evidence of duplication, not a promised reduction for the next package.

### Reliability work alongside these features

- **Installed-wheel lifecycle coverage:** Extend the isolated runtime-wheel consumer beyond a scoped MTA Uri. Add representative unscoped STA/MTA cleanup, synchronous callback close/recovery, and owner-drain reinitialization cases using the installed release artifacts on native x64 and ARM64 across the supported CPython matrix. Keep native, emulated, and compile-only evidence distinct.
- **Read-only lifetime diagnostics:** Expose actionable ownership and apartment state, including pending cleanup and active callback/async blockers, so callers can understand why a close is rejected or deferred. Diagnostics must not retain owners after returning, change native reference ownership, cancel work, or perform foreign-thread cleanup.
- **Strict custom-WinMD validation:** Reject invalid GUID attribute component types and ambiguous required default-interface facts with actionable errors. The shared parser still substitutes zero for wrongly typed GUID components and selects the first default interface; harden those decisions with malformed-metadata fixtures while preserving valid SDK output.

### WinAppSDK follow-up

Improve bootstrap discovery and repeated initialization: retain explicit path/environment precedence, select only candidates matching the requested version and process architecture, reuse compatible initialization, and report conflicting requests clearly. Initialization currently requires a supplied DLL path; this work should reduce manual setup without silently changing the requested runtime or initializing COM on the caller's behalf.

Qualify WinUI behavior separately on an interactive native ARM64 runner as well as x64. The existing ARM64 workflow requires a self-hosted desktop and installed framework; adding discovery or obtaining an emulated pass is not evidence that the live UI path is qualified.

Only promote items to a later release's notes after implementation, integration review, and the relevant native/consumer verification are complete.
